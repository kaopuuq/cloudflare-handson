CLOUDFLARE HANDS-ON

Cloudflareハンズオン：PagesとWorkersで掲示板を公開する

小さな「ひとこと掲示板」を作りながら、Cloudflare PagesとWorkersでWebサイトを公開する流れを一通り体験します。すべて無料プランの範囲で進められます。

はじめに

この資料は説明会のあとに各自で進めるためのものです。上から順に進めれば、最後には投稿を保存できる掲示板がインターネットに公開されます。

フロントエンドの知識は前提にしていません。HTMLを少し読めて、Gitでcommitとpushができれば進められます。

A. Pagesで公開する静的なページをGitHubと連携して公開し、プレビューとロールバックを試すstep-a
B. Workersに移す同じサイトをWorkersで公開し直し、設定ファイルとコマンドに慣れるstep-b
C. 掲示板にする投稿APIを書き、投稿をD1（データベース）に保存するstep-c

配布するリポジトリには、段階ごとにブランチ（step-a、step-b、step-c）があります。途中でつまずいたら、次の段階のブランチに切り替えれば続きから始められます。

この資料の読み方

黒い枠はターミナルで打つコマンドです。右上の「コピー」で写せます。緑の枠の「成功したときの見た目」を開くと、手元で実行したときの出力の例を確かめられます。

画面の項目名はこのように表しています。Cloudflareの画面は変わることがあるので、表記が少し違うときは近い名前の項目を探してください。

git push -u origin step-a:main

1. 全体像と用語

Cloudflareは世界中にあるデータセンターのネットワークの上でサービスを動かしています。ユーザーのアクセスは近くのデータセンターが受け取り、そこで静的なファイルを返したり、プログラムを動かしたりします。自分でサーバーを用意したり管理したりする必要はありません。

この資料で出てくる用語です。

Pages
静的なWebサイトを公開するサービス。GitHubにpushすると、自動でビルドして公開します。
Workers
Cloudflareのネットワーク上でJavaScriptやTypeScriptのコードを動かすサービス。静的なファイルの公開（Static Assets）もできます。Cloudflareは新しく作るプロジェクトにはWorkersを勧めています。
Static Assets
WorkersでHTML、CSS、画像などのファイルをそのまま返す機能。静的ファイルへのリクエストは無料です。
D1
Cloudflareが提供するデータベース。SQLiteと同じSQLで読み書きします。
binding
WorkerのコードからD1などの資源を使うための名前。設定ファイルでDBと名付けると、コードからenv.DBで使えます。
wrangler
Workers、Pages、D1を操作するコマンドラインツール。npx wrangler ...で実行します。
デプロイ
作ったものをインターネットに公開すること。
プレビュー
本番とは別のURLで、変更を公開前に確かめる仕組み。
ロールバック
公開中のものを、以前に公開したものへ戻すこと。
Astro
Webサイトを作るためのツール。.astroファイルはほぼHTMLのまま書けて、npm run buildで公開用のHTMLをdist/に出力します。

2. ハンズオンA：Pagesで公開する

ブランチstep-aの内容を、Cloudflare Pagesで公開します。目安は30分です。

ローカルで表示する

  1. 開発用のサーバーを起動します。 
    npm run dev
  2. ブラウザでhttp://localhost:4321を開き、「ひとこと掲示板」と2件の投稿が表示されることを確かめます。
  3. src/pages/index.astroの投稿の文を書き換えて保存すると、ブラウザの表示がすぐに変わります。確かめたらCtrl+Cでサーバーを止めます。

ファイルの構成は次のとおりです。触るのは主にsrc/pages/とpublic/です。

ファイルの構成
src/pages/index.astro     # トップページ（/）
src/pages/about.astro     # /aboutのページ
src/pages/404.astro       # 見つからないときのページ
src/layouts/Layout.astro  # 全ページで共通の枠（ヘッダーとフッター）
public/                   # 加工せずに公開するファイル（CSS、_headers、_redirects）

.astroファイルは---で囲んだ部分にJavaScriptを書き、その下にHTMLを書きます。{ }の中に書いた値がHTMLに埋め込まれます。

src/pages/index.astro（抜粋）
---
const posts = [
  { name: 'さくら', message: 'はじめまして！', createdAt: '2026-11-01 10:00' },
];
---
<ul class="posts">
  {posts.map((post) => (
    <li><p class="message">{post.message}</p></li>
  ))}
</ul>

公開用のファイルを作るにはnpm run buildを実行します。dist/にHTMLが出力され、Cloudflareにはこのdist/を公開してもらいます。

npm run build

Git連携でデプロイする

  1. Cloudflareのダッシュボードを開き、左のメニューからWorkers & Pagesを選びます。
  2. Create applicationを押し、PagesのタブでConnect to Gitを選びます。Workersの作成画面が先に出るので、Pagesのタブを探してください。
  3. GitHubを選んでInstall & Authorizeで連携を許可し、準備で作った自分のリポジトリを選んでBegin setupを押します。
  4. Project nameにはハンズオンBで作るWorkerと別の名前（cloudflare-handson-pagesなど）を入れます。この名前がpages.devのURLになります。
  5. ビルドの設定を次のように入れます。Framework presetでAstroを選ぶと、残りは自動で入ります。
    項目値
    Production branchmain
    Build commandnpm run build
    Build output directorydist
  6. Save and Deployを押すと、ビルドが始まります。ログが流れ、数分で終わります。
  7. 表示されたhttps://<プロジェクト名>.pages.devを開き、手元と同じページが表示されることを確かめます。

リポジトリの.node-versionには24と書いてあり、Cloudflareのビルド環境はこのバージョンのNode.jsを使います。Astroは古いNode.jsではビルドを止めるので、このファイルは消さないでください。

これで何が起きるようになったか

これ以降、mainブランチにpushするたびに、Cloudflareが自動でビルドして公開し直します。

プレビューを確かめる

main以外のブランチにpushすると、本番とは別のURLでプレビューが公開されます。変更を本番に出す前に、ほかの人に見てもらうときに使います。

  1. ブランチを作り、トップページの説明文を書き換えてpushします。 
    git switch -c change-lead
# src/pages/index.astroの「ひとことを残していってください。」を好きな文に変える
git commit -am "トップページの説明文を変える"
git push -u origin change-lead
  2. ダッシュボードでプロジェクトを開き、Deploymentsにchange-leadのプレビューが出ることを確かめます。
  3. プレビューのURL（https://change-lead.<プロジェクト名>.pages.dev）を開くと変更後のページが見え、本番のURLは変わっていないことを確かめます。
  4. GitHubでPull Requestを作ると、そのブランチのプレビューが作られ、pushするたびに更新されます。確かめたらマージして、本番に反映されることも見てみましょう。
プレビューは誰でも見られる

プレビューのURLは、初期の設定では公開されていて、URLを知っていれば誰でも開けます。検索エンジンには載らないよう、X-Robots-Tag: noindexのヘッダーが付きます。

ロールバックする

本番に出したあとで問題に気づいたときは、以前に公開したものへすぐに戻せます。ビルドをやり直さずに、公開済みのファイルに切り替えるだけなので、すぐに反映されます。

  1. わざと見出しを崩した変更をmainにpushします。 
    git switch main
git pull
# src/pages/index.astroの<h1>を「こわれた掲示板」などに変える
git commit -am "わざと見出しを崩す"
git push
  2. 本番のURLで、見出しが変わったことを確かめます。
  3. ダッシュボードのDeploymentsで、1つ前の本番のデプロイの右にある…からRollback to this deploymentを選びます。
  4. 本番のURLを開き直し、見出しが元に戻ったことを確かめます。
ロールバックしてもGitは戻らない

ロールバックで戻るのは公開中のファイルだけで、リポジトリのmainには崩した変更が残ります。次にpushすると、また崩れたものが公開されます。git revert HEADで変更を取り消してpushしておきましょう。

_redirectsと_headers

public/に置いた2つのファイルで、転送とレスポンスヘッダーを設定しています。どちらもPagesとWorkersの両方で使えます。

public/_redirects
# 古いURLから新しいURLへ転送する（301は恒久的な転送）
/info /about 301
public/_headers
# すべてのページに付けるセキュリティ用のヘッダー
/*
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin

# CSSは1時間キャッシュさせる
/style.css
  Cache-Control: public, max-age=3600

公開したサイトで確かめます。/infoを開くと/aboutに移り、ヘッダーはcurlで見られます。

curl -I https://<プロジェクト名>.pages.dev/info
curl -I https://<プロジェクト名>.pages.dev/
成功したときの見た目

手元でnpx wrangler pages dev distを実行し、同じことを確かめたときの出力です。

3. ハンズオンB：Workersに移す

同じサイトを、今度はWorkersで公開します。目安は20分です。PagesとWorkersでは、同じことを設定ファイルとコマンドで行う点が違います。

  1. 段階Bの内容を自分のmainに取り込みます。 
    git fetch upstream
git switch main
git merge upstream/step-b
npm install
  2. pushする前に、Pagesの自動デプロイを止めます。ダッシュボードでPagesのプロジェクトを開き、SettingsのBuilds & deploymentsでConfigure Production deploymentsを開き、Enable automatic production branch deploymentsのチェックを外して保存します。ハンズオンが終わったら、Pagesのプロジェクトは削除してかまいません。

wrangler.jsoncを読む

段階Bで増えたのは、Workersの設定ファイルwrangler.jsoncです。Pagesで画面に入れていた設定を、ここに書きます。

wrangler.jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  // Workerの名前。公開URL（<name>.<サブドメイン>.workers.dev）に使われる
  "name": "cloudflare-handson",
  // Workersの実行環境の挙動を、この日付の時点のものに固定する
  "compatibility_date": "2026-11-16",
  "assets": {
    // astro buildの出力先をそのまま公開する
    "directory": "./dist",
    // 存在しないURLにはdist/404.htmlを返す
    "not_found_handling": "404-page"
  },
  // バージョンごとのプレビューURLを有効にする
  "preview_urls": true
}

nameは公開URLの一部になります。ほかの人と同じアカウントを使うときは、cloudflare-handson-自分の名前のように変えてください。

まず手元で動かします。npm run previewはビルドしたあと、Workersと同じ動きをするローカルのサーバーを起動します。

npm run preview

コマンドでデプロイする

  1. wranglerからCloudflareにログインします。ブラウザが開くので、Allowを押して許可します。 
    npx wrangler login
  2. デプロイします。 
    npm run deploy

    はじめてのときは、workers.devのサブドメイン（<サブドメイン>.workers.devの部分）を決めるよう求められることがあります。

  3. 出力の最後に表示されるhttps://cloudflare-handson.<サブドメイン>.workers.devを開き、同じページが表示されることを確かめます。

Workers Buildsで連携する

コマンドでのデプロイに加えて、Pagesと同じようにGitHubへのpushで自動デプロイすることもできます。この機能をWorkers Buildsと呼びます。

  1. ダッシュボードのWorkers & Pagesで、先ほどデプロイしたcloudflare-handsonを開きます。
  2. SettingsのBuildsでConnectを押し、GitHubのリポジトリを連携します。
  3. ビルドの設定を次のように入れます。
    項目値
    Git branchmain（本番にするブランチ）
    Build commandnpm run build
    Deploy commandnpx wrangler deploy（初めから入っている）
  4. 設定を保存し、git pushします。Deploymentsにビルドが出て、終わると本番に反映されます。
  5. main以外のブランチをpushすると、Deploy commandの代わりにPreview command（初めはnpx wrangler preview）が動き、本番とは別のプレビューのURLが作られます。プレビューが作られないときは、設定画面で本番以外のブランチのビルドが有効になっているかを確かめてください。

WorkersでのロールバックはダッシュボードのDeploymentsで戻したいバージョンの…からRollbackを選ぶか、次のコマンドで行います。

npx wrangler rollback

4. ハンズオンC：掲示板にする

投稿を受け取って保存するAPIを、Workerのコードで書きます。投稿はD1に保存します。目安は40分です。

git fetch upstream
git switch main
git merge upstream/step-c
npm install

ハンズオンAでsrc/pages/index.astroを書き換えていると、マージで衝突します。そのときは、段階Cのファイルを採ってマージを終えます。

git checkout --theirs src/pages/index.astro
git add src/pages/index.astro
git commit --no-edit
npm install

コードを読む

段階Cでは、wrangler.jsoncに次の設定が増えました。

wrangler.jsonc（増えた部分）
// APIを処理するWorkerのコード
"main": "src/worker.ts",
"assets": {
  "directory": "./dist",
  "binding": "ASSETS",
  "not_found_handling": "404-page",
  // /api/で始まるURLだけをWorkerのコードで処理する。ほかは静的ファイルを返す
  "run_worker_first": ["/api/*"]
},
// D1データベースとの接続。コードからは env.DBで使う
"d1_databases": [
  { "binding": "DB", "database_name": "handson-db", "migrations_dir": "migrations" }
],
// 環境変数。秘密にしない値だけをここに書く
"vars": { "MAX_MESSAGE_LENGTH": "140" }

APIはsrc/worker.tsにあります。URLとメソッドを見て、3つの処理に振り分けています。

リクエスト処理
GET /api/posts新しい順に50件を返す
POST /api/posts送られた名前とひとことを確かめ、D1に保存する
DELETE /api/posts/:id正しいトークンが付いているときだけ、投稿を削除する
src/worker.ts（抜粋）
async function listPosts(env: Env): Promise<Response> {
  const { results } = await env.DB.prepare(
    'SELECT id, name, message, created_at FROM posts ORDER BY id DESC LIMIT 50',
  ).all<Post>();
  return Response.json(results);
}

テーブルを作るSQLはmigrations/0001_create_posts.sqlにあります。このようなファイルをマイグレーションと呼び、番号の順に1回ずつ実行されます。

migrations/0001_create_posts.sql
CREATE TABLE posts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  message TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

npm run devではAPIが動かない

npm run devはAstroだけのサーバーなので、/api/postsは動きません。段階Cではnpm run previewを使ってください。

本番のD1を作る

  1. Cloudflare上にD1のデータベースを作ります。 
    npx wrangler d1 create handson-db
  2. 出力に表示されるdatabase_idを、wrangler.jsoncのd1_databasesに書き足します。 
    "d1_databases": [
  {
    "binding": "DB",
    "database_name": "handson-db",
    "database_id": "ここに表示されたIDを入れる",
    "migrations_dir": "migrations"
  }
],
  3. 本番のD1にテーブルを作ります。--localの代わりに--remoteを付けます。 
    npx wrangler d1 migrations apply handson-db --remote
  4. 変更をcommitしてpushします。Workers Buildsを連携していれば自動でデプロイされます。連携していなければnpm run deployを実行します。 
    git commit -am "D1のdatabase_idを設定する"
git push
  5. 公開したURLを開き、投稿できることを確かめます。ダッシュボードのStorage & DatabasesのD1でhandson-dbを開くと、保存された行を見られます。
ローカルのDBと本番のDBは別のもの

--localで作ったテーブルと投稿は、手元の.wrangler/にだけあります。本番には--remoteで別にテーブルを作る必要があり、手元の投稿は本番に移りません。

環境変数とSecret

Workerに渡す値は秘密にするかどうかで置き場所を分けます。

種類例ローカル本番
環境変数MAX_MESSAGE_LENGTHwrangler.jsoncのvarsに書く（Gitに入る）
SecretADMIN_TOKEN.dev.varsに書く（Gitに入れない）wrangler secret putで登録する

本番に削除用のトークンを登録します。入力を求められたら、推測されにくい文字列を入れます。

npx wrangler secret put ADMIN_TOKEN

登録した値はダッシュボードでも見られず、変えるときは登録し直します。試しにvarsのMAX_MESSAGE_LENGTHを"10"に変えてデプロイし、長い投稿がはじかれることを確かめてみましょう。

型の定義を作り直す

wrangler.jsoncのbindingやvarsを変えたら、npx wrangler typesを実行してworker-configuration.d.tsを作り直します。エディターがコードのenv.DBなどを正しく補完するようになります。

5. 独自ドメインの設定方法

このハンズオンではドメインを買わず、pages.devとworkers.devのURLで進めました。自分のドメインで公開するときの流れだけを紹介します。

PagesWorkers
設定する場所プロジェクトのCustom domainsWorkerのSettingsのDomains & Routes
DNSをCloudflareで管理しているドメイン名を入れるだけで、DNSのレコードと証明書が自動で作られる
DNSをほかの会社で管理しているDNSにCNAMEレコード（<プロジェクト名>.pages.dev宛て）を作れば使える使えない。先にドメインのDNS（ネームサーバー）をCloudflareに移す

DNSをCloudflareに移すには、ダッシュボードでドメインを追加し、表示された2つのネームサーバーを、ドメインを買った会社の管理画面で設定します。移す作業は無料プランでもできます。

6. PagesとWorkersの選び方

Cloudflareは新しく作るプロジェクトにはWorkersを勧めています。Pagesの公式ドキュメントにも、新しいプロジェクトはWorkersで始めるよう書かれています。迷ったら次のように選んでください。

  • これから新しく作るなら、Workers（Static Assets）を選びます。静的ファイルの公開、プレビュー、ロールバック、D1などのbindingは、どちらでも使えます。
  • Cron Triggers（定期実行）、Durable Objects、Workers Logsなど、Workersにしかない機能があります。
  • DNSをCloudflareに移さずに独自ドメインを使いたいときは、Pagesを選びます。
  • すでにPagesで動いているサイトは、急いで移す必要はありません。Cloudflareは移行の手順を公開しています。

7. 無料枠と制限

無料プランの主な上限です（2026年11月時点の公式ドキュメントによる）。上限は変わることがあるので、使う前に公式のページで確かめてください。

サービス項目無料プランの上限
Workersリクエスト1日に100,000回（UTCの0時にリセット）
1リクエストのCPU時間10ミリ秒
静的ファイルへのリクエスト無料（上の回数とは別）
静的ファイルの数と大きさ1バージョンに20,000ファイル、1ファイル25MiB
Pagesビルド1か月に500回、同時に1つ、20分で打ち切り
ファイルの数と大きさ1サイトに20,000ファイル、1ファイル25MiB
Pages FunctionsWorkersのリクエストの回数に含まれる
D1読み込んだ行1日に500万行
書き込んだ行1日に100,000行
保存できる容量全体で5GB、1つのデータベースで500MB
データベースの数10個

無料プランで上限を超えても、料金はかかりません。Workersは上限を超えたリクエストにエラーを返し、D1は次の日（UTC）にリセットされるまでクエリが失敗します。

8. よくあるエラーと対処

起きたこと原因と対処
no such table: postsそのDBにテーブルがありません。ローカルなら--local、本番なら--remoteを付けてwrangler d1 migrations applyを実行します。
Address already in use、ポートが使われているほかのサーバーが同じポートを使っています。そのサーバーを止めるか、npx wrangler dev --port 8790のように別のポートで起動します。
wrangler loginでブラウザが開かない（WSLなど）ターミナルに表示されたURLを、手でブラウザに貼って開きます。
Pagesのビルドが失敗するビルドのログを開き、最初に出たエラーを読みます。手元でnpm run buildが通るか、Build output directoryがdistになっているかを確かめます。
Node.js vXX is not supported by Astro!でビルドが失敗するビルド環境のNode.jsが古いと起きます。リポジトリの.node-version（中身は24）が消えていないかを確かめます。環境変数NODE_VERSIONを設定しても直せます。PagesではSettingsのEnvironment variables、WorkersではSettingsのBuildのBuild Variables and Secretsで設定します。
投稿の削除が401になるAuthorization: Bearer <トークン>のヘッダーがないか、値が違います。本番ではwrangler secret put ADMIN_TOKENで登録した値を使います。
npm run devで/api/postsが404になるAstroだけのサーバーなので、APIは動きません。npm run previewを使います。
デプロイしたのに表示が変わらないブラウザのキャッシュが残っていることがあります。再読み込み（Ctrl+Shift+R）するか、プライベートウィンドウで開きます。
